# 2 枚目のサンプル画像の認識の修正

2026-10-19 にローカルで検証した結果の記録です。この修正は公開中のデモにも反映済みです。最終更新：2026-11-11（現在の状態に合わせて更新）。

## 確認した原因

`Normal-107.jpg` のセグメンテーション出力には、中身の詰まった大腿骨（前景画素 255,050 個）と、脛骨のまわりの細い輪（前景画素 18,705 個）が含まれています。元の処理は、先に `findContours(RETR_EXTERNAL)` を呼び、`contourArea` で輪郭を選んでいました。細い輪が囲む面積は 408,629.5 で、大腿骨の 253,817 より大きいため、細い輪が塗りつぶされ、最終的に脛骨を大腿骨として扱っていました。

修正：まず 8 近傍の連結成分を実際の前景画素数で比べて最大の領域を選び、そのあと外輪郭の抽出、穴埋め、元のモルフォロジー処理と平滑化を行います。モデル、前処理、推論回数は変えていません。

2 枚目のベースラインは、約 `(616, 2618)—(706, 2613)` から `(335, 727)—(719, 732)` に変わりました。修正前に公開中のデモのサンプル解析 API が返していた旧ベースラインは、ローカルの旧ロジックの結果と完全に一致しました。6 枚目のサンプル（Normal-348）にも同じ問題があり、これも修正されました。残りの 8 枚のベースライン座標はまったく変わっていません。現在の公開中のデモは、修正後のベースラインを返します（2026-11-11 に確認）。

- [2 枚目の修正前後の比較](second-sample-before-after.jpg)
- [10 枚すべての修正後の結果](all-samples-after.jpg)
- [画像ごとの数値結果](sample-results.json)

これらの公開サンプルには、人手による正解ラベルがありません。今回の検証は、誤った対象を選ぶ問題の回帰検証であり、Dice、NWI の精度、臨床的な有効性の検証ではありません。

この修正の時点では、両膝の画像も最大の領域だけを選んでいました。その後、Web 版は両膝を膝ごとに計測できるようになりました（README の「Web 版の左右候補と両膝画像」）。デスクトップ版は、今も最大の領域だけを選びます。

## モデルの比較

同じ処理の流れ（512×512 の RGB・ImageNet 正規化、元画像と左右反転の logits の平均、argmax、最近傍補間での復元）で、10 枚のサンプルに既存の ONNX と NWIproject の最良の PyTorch 重みをそれぞれ実行したところ、大腿骨の二値マスクはすべて画素単位で一致しました。

| ファイル | サイズ（バイト） | SHA-256 |
|---|---:|---|
| model_b5_384.onnx | 123976821 | 06dd84da55efdeb685b1b0ea6acc26e81564b0a4a560e619d7687e939d1f64db |
| best_unetplusplus_efficientnet-b5_384scse_highres.pth | 129339712 | 3b7b75c2c086de3debc11410d7c8fe69135444885df0392bf27c8188c25a462b |

この比較で示せるのは、今回の入力で ONNX と PyTorch の出力が一致したことだけで、すべての入力で一致することは示せません。公開中のデモのコンテナイメージに入っているモデルファイル（`/opt/model/model_b5_384.onnx`）の SHA-256 は、上の表の model_b5_384.onnx と一致します（2026-11-11 に確認）。

ローカルの ONNX では、TTA 2 回分の推論が 1 枚あたり約 1.23–1.27 秒でした。実モデルの回帰テスト 1 件のプロセスのピーク RSS は約 1.14 GB（macOS）、PyTorch で 10 枚を比較したプロセスのピークは約 5.33 GB でした。どちらもこのマシンのプロセスで観察した値で、Lambda に必要なメモリの見積もりやハードウェア性能の比較には使えません。2026-11-11 に公開中のデモで 2 枚目を解析したときのレスポンスの `elapsed_ms` は 5366 でした。これはアプリ側で計った時間で、AWS の Billed Duration ではありません。

## テスト

この修正で、アルゴリズムの回帰テスト 3 件と実モデルの回帰テスト 1 件（`tests/test_postprocessing.py`）を追加しました。中空の輪のテストは、修正前は失敗し、修正後は通ります。実モデルのテストは、2 枚目の大腿骨顆部の位置がゆるい範囲に入るかを確かめるもので、「プログラムが落ちなかった」ことを正しく認識できたことと取り違えないようにしています。

現在のテストは全部で 19 件です。学習済みモデルがない環境では 15 件を実行し、モデルを使う 4 件はスキップします。実行方法は README の「テスト」を参照してください。GitHub Actions でも、push と pull request のたびにモデルなしで実行しています。

## AWS の費用と軽量化の提案

今回は、モデルの交換や圧縮は不要です。誤りは後処理にあり、現在の ONNX と最良の重みは、すべてのサンプルで同じ出力を返します。そのため、最小限のコード修正だけをデプロイしました。

公開中の関数は、Arm（arm64）・メモリ 3008 MB・コンテナイメージで動いています（設定は 2026-10-19 に AWS から取得）。呼び出し回数や請求額は取得していないため、下の表は実際の請求ではなく試算です。

[東京リージョンの公式価格 JSON](https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/AWSLambda/current/ap-northeast-1/index.json)（2026-11-11 に取得、publicationDate は 2026-10-30T23:42:55Z）の Arm の第 1 段階のオンデマンド単価は $0.0000133334/GB-s、リクエストは $0.0000002/回です。

1 回あたり 5 秒の課金、画像 1 枚につき解析リクエスト 1 回と仮定し、無料枠を差し引かない場合：

| 月あたりの解析回数 | 費用（Arm・3008 MB） |
|---:|---:|
| 1,000 | $0.196 |
| 10,000 | $1.960 |
| 100,000 | $19.603 |

計算式：回数 ×（3008 / 1024 GB × 5 秒 × GB-s 単価 ＋ リクエスト単価）。[公式の料金ページ](https://aws.amazon.com/lambda/pricing/)によると、無料枠は毎月 100 万リクエストと 40 万 GB-s です（2026-11-11 に確認）。解析 1 回は 14.6875 GB-s なので、無料枠を解析だけに使えば、月に約 2.7 万回まで収まる計算です。どれだけ差し引けるかは、アカウントの条件とほかの関数の使用量によります。上の金額には、コールドスタートで増える課金時間、ページや画像のリクエスト、ECR のイメージ保存、ログ、通信量、税、プロビジョニングされた同時実行を含めていません。

今後、費用を最適化するときは、まず CloudWatch の REPORT から Billed Duration・Max Memory Used とコールドスタートの割合を取り、メモリ設定ごとの GB-s を比べます。[Lambda の CPU はメモリ設定に応じて増える](https://docs.aws.amazon.com/lambda/latest/dg/configuration-memory.html)ため、メモリを下げるだけで安くなるとは判断できません。公開サンプルの結果を事前に計算しておくことや、不要な重複推論を減らすことも、優先して検討する価値があります。INT8 などの量子化には、追加のキャリブレーションと、正解ラベル付きデータでの輪郭・NWI の回帰テストが必要です。現時点では、モデルをそのまま差し替えて公開するだけの効果を示す根拠はありません。
